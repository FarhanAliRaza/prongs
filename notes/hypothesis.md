# Hypothesis: an agent-native test runner for Python

> Reviewed by [[verdict]] (July 2026) — corrections folded in below. Its one-line thesis is worth keeping: **speed is the demonstration; safe incremental execution is the technical contribution; agents are the highest-frequency client.** Architectural rule: real pytest stays the semantic authority (collection, fixtures, plugins, execution); we build an incremental runtime *around* it. Delegating to pytest shrinks the compat surface but does not zero it — process lifetime, scheduling, and fixture/state lifetime are all observable pytest semantics, so uncertain configurations must fall back to a fresh pytest process.

**The reframe (July 2026, after field research):** the original hypothesis below was framed as "make pytest fast for humans." The research says humans mostly tolerate this pain with free workarounds (xdist, --reuse-db, ripgrep hacks) — collection/startup complaints are real and angry but concentrated in large repos, and nobody has ever paid for a runner binary. The customer who *can't* tolerate the pain, and whose usage is exploding, is the **coding agent**. Tests are the agent's reward function: SWE-agent averages 12–15 turns per task (newer agents 30–80), a large fraction of them test runs; devs run 10–20 agents in parallel across worktrees; RL labs re-architect entire clusters around test-execution throughput. A human runs the suite a few times an hour. An agent fleet runs it hundreds of times. Every term in the cost equation below gets multiplied 10–100x — and the agent has failure modes humans don't (2-minute tool timeouts that kill sessions, context exhaustion from verbose tracebacks, flaky tests that poison the reward signal at 100–200k tokens per flake chase).

So the product is not "pytest but faster." It's **the verification layer for Python coding agents**. Speed is the demo; the machine interface and the dependency database are the product.

## What agents demonstrably need (ranked by evidence strength)

1. **Low latency / fast startup.** Claude Code's Bash tool defaults to a 2-minute timeout; long suites literally kill agent sessions. Anthropic's own best-practices docs ship the workaround as prompt text: "Prefer running single tests, not the whole suite, for performance." A runner that makes the whole affected set finish in seconds deletes this entire failure class.
2. **Test selection exposed to the agent as a queryable API.** The strongest single data point in the research: TDAD (arXiv 2603.17973) gave an agent test-impact analysis and cut the *test-level* regression rate 6.08%→1.82% — and merely prompting "run tests first" without selection info made regressions *worse* (9.94%). Agents guess badly at which tests matter; the runner has to compute it. Think `fastest affected --diff HEAD` returning a test list, not just an internal optimization. *Hedge (per [[verdict]]): in the 100-instance phase resolution actually fell slightly (31%→29%) and instance-level regression rate didn't improve; n is small (100+25), no significance tests, and the integration was just a static test-map file + grep. So TDAD supports "expose impact context to agents" — it does NOT validate any daemon/fork/scheduler architecture. That has to earn its own evidence.*
3. **Structured, token-frugal output.** A cottage industry of pytest MCP wrappers exists purely because raw pytest output is agent-hostile. Native output should be a pass/fail schema with token-budgeted, diff-aware tracebacks — context exhaustion is the #1 agent killer per Anthropic's own docs.
4. **Isolation for parallel agents.** The top documented multi-worktree failure modes are test-infra failures: port collisions from test servers, agents corrupting each other's test DBs. ~~Fork gives every agent pristine CoW DB state for free~~ — **corrected:** fork copies *in-process memory* (Python objects, in-memory caches, warm imports), not external infrastructure. A Postgres server is another process; forking just duplicates the client connection fd, which is a hazard to close/reopen, not a snapshot. Real isolation needs explicit adapters per resource: Postgres → template-clone / per-worker DB / transaction rollback (Django already does the latter two — that's the actual mechanism when the demo "works" on Django), Redis → namespace, HTTP → port allocation, filesystem → per-run tmp root. These adapters are *more* valuable to parallel agents than forked-memory snapshots.
5. **Determinism / flake resistance.** Flaky tests poison both interactive loops and RL rewards ("low noise" is a pillar of verifier's law). Built-in flake detection and quarantine is a feature, not an afterthought — it's the one thing enterprises demonstrably pay for today (Trunk.io pivoted its whole business to it).

## The cost equation (original hypothesis — still valid, now with a bigger multiplier on every term)

"Rust rewrite" alone buys almost nothing here — test time is mostly *Python executing your code*, which you can't Rust away. The trick is that a test run's wall-clock decomposes into five costs, and each one dies to a different mechanism:

**Total time = startup + collection + (selected tests × per-test overhead + actual test body) ÷ parallelism**

**1. Startup → kill with warm daemon *generations* + fork.** The daemon boots once: interpreter, pytest machinery, your conftest, and the heavy imports (Django setup, torch, whatever). Every subsequent run **forks** from that warm process — copy-on-write means a fork costs ~1-5ms instead of a 2-8 second cold start. This is the Instagram trick, and Discord built exactly this internally ("10x local test iteration") without productizing it. Key design correction from [[verdict]]: **the warm image is a disposable cache, never authoritative state — think generations, not one immortal process.** Each generation is identified by a fingerprint (interpreter + installed dists + pytest/plugin set + config + conftest hierarchy + imported app-code hashes); any change that can't be confidently localized destroys the generation and a fresh one warms up. When a warm module's source changes you never reload — you retire the generation. Fork safety is real (Python 3.14 switched the default multiprocessing start method to `forkserver` precisely because fork + threads is broken; warmed Django/asyncio/gRPC/CUDA processes carry threads, event loops, sockets, pools), so fork is **Linux-first, opt-in, guarded by unsafe-state detection, with post-fork re-init hooks and automatic fallback to a fresh pytest process**. That fallback ladder — `fresh` (semantic oracle) / `warm` (cached generation, no cross-run fixture reuse) / `optimized` — is what makes the fast path trustworthy. Generation invalidation is Rust's first real job. *Prior art check: rpytest ships almost exactly this architecture (daemon + Rust CLI + warm workers) and its published number is 1.9× on a 480-test full-suite run, with its own docs marking hooks/flags/collection-order as partial-compat. Two lessons: warm-process alone is a ~2× whole-suite trick, and "real pytest inside the worker" ≠ zero compat risk. Our multiplier has to come from selection × warm start on the single-change loop — a different workload than "whole suite, slightly faster," and our differentiation from rpytest.* *Agent angle: this is also what makes hundreds of runs/hour per worktree viable at all.*

**2. Collection → accelerate with static AST parsing, but as a speculative index, never the source of truth.** pytest discovers tests by *importing every test module*, which transitively imports your whole app. Field evidence this is real pain: "15s to collect on our big Django app, so we added a ripgrep util"; "30s to run a single 200ms test with `-k`"; a pytest contributor estimates pytest is "a bit more than 10x slower than it strictly needs to be." rtest proved the speed: parse statically, never import, 5-25x on normal repos, 100x+ on monorepos. But collection is *inside* pytest semantics — plugins implement custom collectors, generate/reorder/remove items via `pytest_collection_modifyitems`, parametrize dynamically, and behave differently per conftest hierarchy. rtest's own docs admit repos that fail under its collector while working with pytest. So the rule is **"static analysis proposes, pytest disposes"**: static parsing owns fast search, candidate node IDs, and changed-line→test mapping; real pytest owns canonical node IDs. Classify each module `STATIC_SAFE` / `CANONICAL_REQUIRED` / `UNKNOWN` by diffing static vs. canonical results after every real collection, and only use the fast path where parity has been established and the fingerprint is unchanged. *Caution from the graveyard: rtest/rustest/rytest all stalled at <30 GitHub stars on exactly fixture/conftest/plugin compatibility. Collection is the easy 20%; compat is the moat pytest already owns (989M downloads/month).*

**3. Selection → the biggest multiplier, and the most trust-fragile.** This is where 10x lives, and it's where the agent story is strongest (see TDAD above). Per-test coverage (cheap now via `sys.monitoring` in 3.12+, callback-based instead of tracing every line like the old `sys.settrace`) gives you a map: *test X touched files/functions A, B, C*. Diff comes in → invert the map → run only the affected 3% of the suite. **The lesson from pytest-testmon's decade of failing to break out (~3% of xdist's downloads, "tried it, didn't really work that great" is the recurring verdict): correctness receipts are the product, not the optimization.** People abandon selection the first time it wrongly skips a test. So: unmapped tests always run, dynamic imports/data files/env vars force conservative inclusion, a periodic full run re-validates the graph, and every skip is *explainable* — the runner can show why a test was safe to skip. Receipts are not a mathematical proof of safety (impossible in dynamic Python) — they're a **transparent, auditable conservative policy**: conftest changed → run its whole scope; pytest config changed → recollect and broaden; lockfile/plugin version changed → fresh generation; new or unmapped test → always run; changed file with no reverse edges → package/repo fallback; incomplete subprocess/thread attribution → broaden. Two implementation notes: coverage.py's `sysmon` core doesn't support dynamic contexts (exactly the per-test attribution we need), so we build our own narrow recorder — function-entry events, active-test ID set at setup/call/teardown boundaries, explicit "observation incomplete" marking — which is also where the differentiating engineering lives. And a factual fix: **testmon is MIT-licensed, not AGPL** — its failure to break out is a trust/visibility story, which sharpens (not weakens) the receipts thesis.

**4. Per-test overhead → fork-per-test and fixture snapshots — scoped honestly.** Expensive session fixtures: run them once in the warm parent, then fork per test — the test gets a pristine copy of *in-process* post-fixture state via copy-on-write (Python objects, in-memory caches, possibly in-memory SQLite), and teardown becomes free because you just kill the process. What fork does **not** snapshot: anything living in another process — Postgres state, Redis, spawned servers. For those, isolation comes from the explicit adapters in item 4 above (Django's transaction-rollback + per-worker DB clone being the canonical example). pytest's fixture resolution and assertion rewriting can move to Rust with cached results — smaller win. *Note from research: nobody complains about per-test overhead as such; this matters mainly because it pairs with resource adapters as the isolation mechanism agents need, not because it's a felt pain.*

**5. Parallelism → a real scheduler.** pytest-xdist is a solved-with-papercuts incumbent (145M downloads/month — everyone's first answer), so this is not the wedge. And a correction: xdist ships a `worksteal` distribution mode and a custom-scheduler hook today, so "work stealing" alone is not novel. The papercuts that still compound at agent scale: per-worker re-collection, no duration awareness, no setup-topology awareness (arbitrarily splitting tests that share an expensive module fixture costs more than it saves). The scheduler thesis has to be: duration-history + fixture-affinity grouping + isolation constraints + failure-first ordering, fed by the coverage DB you're already keeping.

The endgame is still **content-addressed caching**, the cargo/Bazel model: if the hash of (test code + everything it transitively touches + fixture state) hasn't changed, the previous result is valid — don't rerun at all. Nobody has made this work for mainstream Python because tests aren't hermetic, but you don't need perfection — "safe for 80% of tests, conservative fallback for the rest," and the coverage database is exactly the dependency-closure record that makes the hashing possible. This is also the only layer anyone has ever monetized (Nx Cloud's remote cache; Bazel's cache via BuildBuddy/EngFlow).

## Honesty section

None of this speeds up the test body itself — a test that spends 4 seconds hitting real Postgres spends 4 seconds regardless. Field research confirms slow test bodies (Django DB setup/migrations above all) are the **#1 complaint by volume**. The levers there are selection (don't run it), parallelism, caching (don't run it again) — and the fixture-snapshot fork, which does directly attack the DB-setup case. Pitch per-*run* speedup, never per-test. Same discipline for headline numbers: "6 minutes → 3 seconds" requires skipping nearly all test bodies, so it must always be a *measured result on a named repo*, never the default promise — and never multiply independent microbenchmark ratios into a combined claim. Also: at PyPI's scale, GitHub Actions plumbing was ~100% overhead on top of pytest itself — CI-side wins need the remote cache, not just a faster local runner.

## Business reality (candid)

- **Standalone "fast runner" company: the precedents say no.** Launchable (best-funded pure test-impact play) exited quietly to CloudBees in 2024. Datadog and CircleCI bundle test speed as platform add-ons. Nobody pays for a runner binary.
- **The Astral/OpenAI overhang is explicit, not hypothetical.** Charlie Marsh publicly named test infrastructure / "really fast verification" as a candidate next project; OpenAI **announced its intent to acquire** Astral (March 2026) into the Codex team explicitly to cover "verifying results" — as of July 2026 the deal is announced, not closed. The direction is real; the "12–24 month window before a free, polished, pytest-compatible runner" is our speculation, not evidence — treat it as a planning assumption, not a fact.
- **The only configuration with a real business behind it: the Nx Cloud playbook.** Free OSS runner as the wedge; paid cloud for remote result caching, cross-CI test-impact database, flaky quarantine. Permissive license, enterprise sales motion, agent-infra positioning ("the verification layer for Python agents" — the gap nobody serves: sandboxes like E2B/Modal/Runloop solve *where* agent code runs, not *how fast tests run inside*; Nx does affected-selection for JS, no Python-native equivalent exists).
- **Strongest risk-adjusted fit: as a feature.** Shipped inside an existing product ("your app's tests run in seconds; agents building on it verify instantly") the tech is valuable without winning the runner war against pytest and whatever Astral ships.

## Build order (revised for the agent-native frame)

1. **`sys.monitoring` coverage layer** — unchanged as the wedge; it's the load-bearing component that selection, caching, and duration-aware scheduling all query. The dependency database is the moat.
2. **Selection API with receipts** — promoted from #4-ish to #2. `affected --diff` as a first-class, explainable, conservatively-correct query. This is the TDAD result productized, and the thing agents can't compute themselves.
3. **Structured agent-facing output** — new. Pass/fail schema, token-budgeted diff-aware tracebacks, MCP-native. Cheap to build, immediately differentiating, and it's what makes agents (and agent vendors) adopt the runner at all.
4. **Daemon/fork runtime** — the latency killer. Disposable warm *generations* with fingerprint invalidation, fresh-process fallback always available, post-fixture fork snapshots for in-process state, plus explicit external-resource adapters (Postgres clone / Redis namespace / port allocation) for parallel-agent isolation.
5. **Static collection** — a speculative acceleration cache behind canonical pytest collection ("static proposes, pytest disposes") — sidesteps the fixture-compat graveyard.
6. **Scheduler, then content-addressed caching last** — caching is the endgame and the monetization surface (remote cache = the paid cloud).

The through-line: every component that was "an optimization for humans" in the original framing is "a capability agents structurally lack" in this one. That's the difference between competing with free workarounds and serving an unserved customer.
