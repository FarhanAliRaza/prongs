# Lessons from Anthropic's test-impact-analysis scaling story

> Source: Sachin Malhotra, "Agentic coding is straining CI. Here's how we scaled test impact analysis at Anthropic" (claude.com/blog, 2026-09-14, read 2026-09-24). Thesis: at agent scale a test-selection service's bottleneck is **evidence freshness**, not selection compute — a selector fed by a lagging recorder silently makes wrong decisions, and the v0 mistake that caused the lag was a *stateful single writer*, not a slow algorithm. Numbers: engineers ship 8x the code per quarter vs 2021–2025, Claude authors 80% of it, tests 10x on flat headcount, **CI jobs 25x in six months**. Three patches (double the cores: ~70 days; shard per package: 29 days; daily restarts: <1 day), then a three-week redesign by one engineer ("a year ago it would have been closer to a quarter").

## What the article actually describes (so we don't over-read it)

- Two components. A **listener** records the results of every CI run. A **selector** "reads the test result history and determines which tests run on which opened PRs." Described as deterministic. Nothing about coverage maps, dependency graphs, or selection accuracy — the algorithm is not disclosed. Their evidence is **per-test result history** (outcomes over time); ours is a **per-test dependency set** (test → code units, one snapshot). A production TIA needs both. We have only the first.
- The failure. Listener lag → results not recorded → selector runs on stale data: "running tests that were already super flaky", fixed or new tests don't run until it catches up, bad merges break everyone's PRs. The v0 was a single process because "a single writer needed to apply the results" to per-test history — which is exactly what made it unshardable.
- The fix. Stateless listener workers append each result to a journal in an in-memory store and move on; "a small separate consumer process rolls the journal up into per-test history every few seconds"; the selector queries the roll-up. More expensive to run, trivially scalable, trivially profilable. Backlog graph ("queued, unprocessed job-result events") grew week over week before cutover, flat after.
- Operations. A Claude session watched the lag metric for months — "anytime the listener lag would get more than 50,000 jobs behind, Claude would ping me" — and wrote the sharding code and the post-cutover tuning. The agent is both the load and the operator.

## The same failure exists in our PoC, in local form

Our "listener" is `pytest --fastest-cov` → `mapdb.dump()`: one full instrumented run replaces the map. Nothing else feeds it. All of the following is visible in the code today:

1. **The map decays silently with every edit.** `run` and `affected` never record coverage by default — `__main__.py` invokes pytest without `--fastest-cov` in both the daemon child and the subprocess fallback — so the map reflects the commit it was built at, forever. Edit E1 makes test `t` start calling `g` (a new edge nobody observed); edit E2 changes `g`; `select()` skips `t`. That is the testmon miss, and it is precisely "the selector was using stale data". Our harnesses never see it: `bench/replay.py` unlinks and rebuilds the map at every commit, `bench/mutate.py` asserts a map built at the diff base. Both validate selection *given a fresh map*; neither measures our own listener lag.
2. **No provenance.** `mapdb.py` creates a `meta` table and never writes a row. The map doesn't know the commit or tree it was observed at, `select()` can't distinguish fresh evidence from forty-commits-old evidence, and `--base HEAD` silently assumes map@HEAD. The skip receipt in `__main__.py` is a constant string — [[verdict]]'s `graph_generation` / `last_observed_run` fields don't exist yet.
3. **The write path can't absorb partial runs.** Even if a selected run recorded coverage, `dump()` upserts by *replacing* each test's links — right for the tests that ran — but it also replaces `__collection__` with that run's partial import-time set, shrinking the run-all guard. Replace-in-place is the single-writer design: correct only when the writer is a whole-suite run. Two worktrees or a daemon child and a CI job writing one map is the corner Anthropic's v0 sat in.
4. **No per-test history.** `tests` holds one `status` and one `duration`. Flake detection ([[hypothesis]] need #5, "the one thing enterprises demonstrably pay for") is impossible on this schema — and flakiness is the first thing the article's lagging selector got wrong.

## Adopt NOW — schema-level, cheap; the article's regret was the data model, not the perf

> **Status (2026-09-24): 1–4 implemented** — `mapdb.py` (journal: `runs`, `observations`, content-addressed `dep_sets`, `blobs`; roll-up: `tests`, `current_links`, one `fold_run` used incrementally and by `rebuild_rollup`; v1 maps migrate into run #1), `provenance.py` (HEAD + dirty files with content hashes *and content* at start and end of every run), `select.py` (evidence in every result; selection per observed tree, so a recorded partial run is credited exactly and a re-edited dirty file is line-diffed against what the run saw), `fastest run --record` (selected runs feed the journal; summary reports selected vs ran vs recorded). Tests in `tests/`. Two policy changes made while doing it: a test module's changes select that module (never run-all), and a changed test module whose known tests can't all be found statically is run as a whole file.

1. **Journal + roll-up, in SQLite.** Every run — full, selected, daemon child — appends to `runs(id, started_at, tree_hash, scope)` and `observations(run_id, test_id, status, duration, deps)`: append-only, any writer, nothing to coordinate beyond WAL. A roll-up (in-process at run end, or lazily at select time) folds observations into the current view: deps per test, `last_observed_run`, a pass/fail window. The selector reads the roll-up only. `__collection__` becomes a per-run, per-collected-module observation that the roll-up unions — never replaced.
2. **Provenance in `meta` and in every receipt.** Record the tree/commit the evidence was observed at, the run scope, the recorder fingerprint. `affected` returns `evidence: {observed_at, commits_behind, tests_refreshed_since}`, and if the requested diff base isn't the map's base, diff against the map's base or say so. This is "instrument your services to act as Claude's eyes and ears" turned inward: the agent is our consumer, and it cannot see lag we don't print.
3. **The in == out invariant.** Article: "ensure that the same number of CI jobs coming in equals the same going out." Ours: every test that ran has an observation from *this* run, and every selected test actually ran. Assert selected vs ran vs recorded at the end of `run` and put the mismatch in the JSON, not on stderr.
4. **Feed the map from selected runs.** With (1) in place, enable the recorder in daemon children and the subprocess fallback. Measured overhead is 1–13% ([[poc-results]]); a stale map costs more than that the first time it skips wrongly. Each edit's run then refreshes exactly the tests it touched, which is what closes the decay in finding 1.

Freshness also becomes a broadening rule, alongside conftest/import-time/unmapped: **stale evidence → broaden, never guess.** A test whose last observation predates changes in files it touches is selected, with the receipt saying why.

## Adopt at scale, not before — but stop painting over it

- **Stateless workers, one roll-up consumer** is the Rust daemon in [[verdict]] and the flat interned bitmap DB in [[data-oriented-design]]. The article adds the operational shape — writers never touch the roll-up; the roll-up is a derived view rebuildable from the journal — and a reason to pull the trigger earlier than "when it shows in the profile": "assume your architecture will be at a 25x load within two quarters" and "account for 10–20x the perceived scale in your v0 designs as long as your budget allows", where the budget is now three weeks, not a quarter.
- **The stale-image daemon.** The daemon already refuses to run on a stale-beyond-repair image (`StaleWarmImage`) and the CLI runs cold — the correct never-wrong posture. Missing is the other half: *measure* the lag (image age vs newest project mtime, cold fallbacks per hour) and re-warm in the background so warm forks always come from a fresh generation. A daemon that can only detect staleness is Anthropic's "daily restart" patch.
- **Multi-worktree.** `.fastest/` is per checkout, so 10–20 agent worktrees means 10–20 cold map builds (wagtail: 331s each). A shared journal keyed by tree hash lets worktrees pool observations; the roll-up is per (repo, generation). That seam is also the paid cross-CI database in [[hypothesis]]'s business section — the article is a first-hand account of that product under 25x load, and its scaling problem was ingest, not query.

## Validated already, worth naming

- **Fallback-first.** Their lagging selector had no fallback and degraded silently; ours broadens to `run_all` on conftest / import-time / unmapped, and the daemon refuses rather than runs wrong. Keep it.
- **"Machine-readable results must come from inside the run"** ([[poc-results]] finding 4). Their listener is that principle at CI scale.
- **Agents as the client.** 80% Claude-authored, tests 10x on flat headcount, 25x CI jobs: [[hypothesis]]'s "an agent fleet runs the suite hundreds of times an hour" is no longer a projection — it is a published number from the most agent-heavy codebase there is.

## Honest scope limit

The article is about a CI service under fleet load; we are a local runtime under one agent's loop. Their bottleneck — ingesting multiple job results per second — does not exist for us: a selected run writing thirty observations to SQLite is nothing. What transfers is the *shape* of the failure, not its scale: a selector whose evidence goes stale without knowing it. And because the article discloses no selection algorithm and no accuracy numbers, it says nothing about whether coverage-map selection is what Anthropic runs. Cite it as validation of the problem and of the listener/selector decomposition, not of our approach.

## The meta-lesson

Three patches — more cores, sharding, restarts — each bought less time than the last because each attacked the symptom. The fix was one representational change: history as an append-only journal with a derived roll-up, which made writers stateless, sharding trivial, and lag measurable. Same lesson as [[data-oriented-design]]: our observation journal is simultaneously the map builder, the freshness evidence in every receipt, the flake-history store, and the multi-worktree/CI sync unit. Get that one write path right now, while the schema is thirty lines and nothing depends on it.
